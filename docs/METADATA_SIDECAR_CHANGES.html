Issue #12 · v0.6.2

Stop writing overlays into the user’s clone

Generated .metadata.benedict files used to be written next to source. Default workspace mode is a symlink, so those writes went through into the checkout. They now live in a workspace sidecar. The clone is read-only.

Constraint. Benedict may read through the repo symlink. It must not create, modify, or delete any file whose resolved path is inside the user’s clone.

Before and after

Before — write through the symlink
workspaces/C123/
  mkarots/benedict → ~/Projects/benedict
    src/commands/
      .metadata.benedict   ← leak

~/Projects/benedict/
  src/commands/
    .metadata.benedict   ← git status
After — sidecar outside the symlink
workspaces/C123/
  mkarots/benedict → ~/Projects/benedict
  metadata/mkarots/benedict/
    .metadata.benedict
    src/commands/
      .metadata.benedict

~/Projects/benedict/
  src/commands/         ← unchanged

Path rule

sidecar = workspace_root / ".benedict" / "metadata" / repo / relative_dir / ".metadata.benedict"

repo is the full resource name (org/repo). The first path component is not stripped.

Write vs read

ActionBehavior
Write Sidecar only. Missing workspace or repo fails. No in-tree fallback.
Read Sidecar, then leftover in-tree file, then None.
Search Returns source-relative dirs (src/commands), never sidecar paths, so directory boost still matches real files.
Cleanup Does not delete leftover in-tree overlays.
